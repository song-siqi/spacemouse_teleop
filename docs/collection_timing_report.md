# 采集时间戳、延迟与离线对齐报告

> **历史阶段说明（2026-09-11 更新）：** 下文记录 raw v2 / 30 fps 阶段及独立 TCP 30000 探测；其中“当前”“尚未接入”“后续方案”均指当时状态。现在已经实现 raw v3 原生视频、逐帧时间索引、被动机器人报告与持续时钟证据，默认相机为 640×480、60 fps。高频 raw 录制已完成并通过现场验证；最新实际遥操结果和后续同步事项见 [raw v3 验证](collection_raw_v3_validation.md)，现行契约见 [raw v3 格式](collection_format.md)，旧数据契约见 [v1/v2 参考](collection_format_v1_v2.md)。以下实验数值保留，不将旧数据重标为 60 fps。按最新范围，离线对齐与数据后处理将在本仓库作为独立阶段实现，详见 [C6 计划](../PROGRESS_PLAN.md#c6--本仓库离线数据处理计划中尚未实现)；目前尚未实现。

日期：2026-09-10。被检查的代码基准：`de026f8`；Python 3.12、xArm SDK 1.18.4、机器人固件 v2.5.5。

本报告整理已有真实轨迹分析、只读相机/查询并发测试，以及 TCP 30000 时间戳反馈测试。整理文档时没有重新连接硬件。测试没有使能、运动、夹爪动作或控制器配置写入；生产采集代码和配置未改变。本文只讨论 observation 的来源时间、保存和对齐，不讨论 action 或推理时序。

证据保存约定：报告及统计可以随仓库提交；`data/`、`logs/` 和 `/tmp/` 路径仅用于定位本机证据，不随 clone 提供，也不保证临时原始文件长期存在。当前 raw v1/v2 的正式约定仍以 [格式文档](collection_format_v1_v2.md) 为准；本文的后续方案尚未实现。

## 1. 结论与证据边界

- 当前三路 640×480、30 fps RGB 与原有 30 Hz 关节/TCP、20 Hz 夹爪查询的测试未显示通信带宽饱和；接收时间配对仍有明显来源时间差。
- 已保存相机帧有 SDK 时间戳和时间域。已有轨迹中，SDK 帧时间到应用取得帧的估算中位差约为 **29.59 / 29.67 / 14.83 ms**，不能解释为经过标定的物理成像延迟。
- 本机 TCP 30000 在 60 秒静止测试中返回 **14,792 包，约 246.518 Hz**。每包有微秒单位的设备时间戳、实际关节与实际 TCP。该通道尚未接入生产采集。
- 报告返回频率已验证；实际测量刷新率、时间戳对应的内部事件、机器人与相机共同时间轴的误差仍未验证。已有约 30 Hz 查询的运动证据见 [频率验证](collection_frequency_validation.md)，不能代替新通道约 247 Hz 的运动验证。
- 后续可以将选帧、插值和 20 Hz 对齐放到离线。采集端需要保留**原生样本、原始时间及可解释的时钟依据、来源索引和完整性信息**。只有一个未说明时钟的 timestamp 数字不够。

## 2. 当前时间字段的含义

| 时间/索引 | 当前含义 | 不应据此推断 |
| --- | --- | --- |
| observation `timestamp` | 主机 monotonic 上的固定 20 Hz 网格 | 所有来源在该时刻同时测量 |
| 相机 `device_timestamp_ms`、`timestamp_domain` | SDK 提供的帧时间及时间域；本条实测为 `global_time` | 已经硬件同步，或就是经过标定的曝光中点 |
| 相机 `received_at` | `try_wait_for_frames` 返回后记录的主机 monotonic 时间 | 设备成像时刻、USB 包到达驱动的时刻 |
| 状态 `query_started_at` / `query_finished_at` | 主机调用查询前后的时间 | 内部测量一定发生在此区间；返回值可能来自缓存 |
| 状态/夹爪 `received_at`、本地 `sequence` | 主机取得结果的时间、采集侧来源计数 | 每次都是新的底层测量 |
| `video_frame_index` / `video_pts_s` | 视频内定位；当前 v2 为 `k` / `k / sample_hz` | 相机原始帧号或真实采样时间 |
| session UTC/monotonic 锚点 | 本机两类时钟在会话开始时的对照 | 机器人时钟已同步，或跨重启可直接比较 monotonic |

当前采集器按 `received_at <= 网格时间` 选择各来源最近的一条：

```text
age_s = 网格时间 - 主机收到该来源的时间
```

`age_s` 不含设备产生数据到主机取得数据之间的时间。`max_camera_age_s` 等配置是质量门槛，不是延迟标定值。实现见 [相机采集](../src/spacemouse_teleop/sensors/realsense/capture.py)、[状态查询](../src/spacemouse_teleop/backends/xarm6_camera/state.py) 和 [observation 选择](../src/spacemouse_teleop/recording/collection.py)。

## 3. 已有真实轨迹的相机时间分析

来源：`data/collections/video_demo/session_20260910T181132.876640Z_463e0bd2/episodes/episode_000001`。共 1258 个 observation，固定 50 ms 网格；三路均为 `timestamp_domain.global_time`。

使用 session UTC/monotonic 锚点作近似转换：

```text
offset = session_utc_seconds - session_monotonic_seconds
估算帧到应用时间差 = received_at + offset - device_timestamp_ms / 1000
估算帧到网格时间差 = observation_timestamp + offset - device_timestamp_ms / 1000
```

假设会话期间主机 UTC/monotonic 偏移稳定，且 SDK 时钟映射有效。结果包含 SDK 时间语义和映射误差，不是曝光到应用的精确标定。

| 相机角色 / SDK 序列号 | 帧时间→应用取得，中位 | 帧时间→网格，中位 / P99 / 最大 | 接收后 age P99 |
| --- | ---: | ---: | ---: |
| wrist / 215122252880 | 29.59 ms | 46.26 / 62.63 / 62.98 ms | 33.02 ms |
| fixed_1 / 311322303615 | 29.67 ms | 46.50 / 62.87 / 63.24 ms | 33.15 ms |
| fixed_2 / 311322303806 | 14.83 ms | 31.67 / 48.06 / 48.44 ms | 33.18 ms |

三路已选帧接收时间差 P99 / 最大为 **31.09 / 33.05 ms**；按 SDK global time 计算则为 **44.07 / 45.03 ms**。相同 observation 行号不代表相同设备帧时间。

补充只读探测发现，三路均支持 `frame_timestamp`、`sensor_timestamp`、`time_of_arrival`、`backend_timestamp`、`actual_fps`；这些附加字段目前没有保存进生产 raw。该次 RGB 帧不支持 `actual_exposure`，应明确不可用。新增记录前需要核实实际单位及事件含义，尤其不能仅凭字段名解释 `backend_timestamp` 的数值。

RealSense 将设备帧时间映射到主机系统时钟后得到 `global_time`；`frame_timestamp` 对应开始读出/传输，`sensor_timestamp` 对应设备计算的曝光中点。可以先按设备帧时间约定对齐，不进一步补偿成像过程，但应保存时间定义。[librealsense v2.58.4 时间定义](https://raw.githubusercontent.com/realsenseai/librealsense/v2.58.4/include/librealsense2/h/rs_frame.h)

## 4. 机器人带设备时间戳的反馈

### 4.1 只读方法与结果

TCP 30000 主动推送。诊断只连接并接收，没有向该端口发送应用数据；另通过 `SDKChannel(writable=False)` 查询身份、状态和位姿作静态交叉核对。测试未开启相机、预览、遥操或 episode 写盘；原始报告写入临时诊断文件。

| 指标 | 结果 |
| --- | ---: |
| 采集持续时间 | 60.004 s |
| 报告数量 / 平均频率 | 14,792 / 246.518 Hz |
| 实际包长度 | 784 bytes |
| 时间戳单位 | μs，大端 uint64 |
| 设备时间戳间隔：中位 / P99 / 最大 | 4.030 / 5.859 / 6.001 ms |
| 主机接收间隔：中位 / P99 / 最大 | 4.033 / 5.841 / 6.144 ms |
| 不递增时间戳 / 设备间隔大于 10 ms | 0 / 0 |
| 机器人状态 | 全程 state 4，静止 |
| 不同关节 / TCP 向量 | 16 / 16，各变化 15 次 |

平均频率按 `(包数 - 1) / (末包接收时间 - 首包接收时间)` 计算。包内时间约每个主机秒增加 1,000,005 个计数，支持微秒单位的解释，但不是时钟精度标定。时间戳连续也不能被描述为严格证明设备从未遗漏内部周期。

当前新固件文档标称 250 Hz（力矩传感器为 200 Hz），早期发布说明标称 200 Hz。这里采用 v2.5.5 的实测，不从其他版本外推。[官方读取示例](https://docs.supportarticle.ufactory.cc/zhHans/support_articles/developer/firmware/how-to-get-the-real-time-data-via-tcp-30000-port.html)、[数据布局](https://docs.supportarticle.ufactory.cc/zhHans/support_articles/developer/firmware/data-description-of-tcp-port.html)、[V2.1.0 发布说明](https://docs.releasenote.ufactory.cc/release_note/studio_2.1.0.html)

### 4.2 数据解释与接入边界

- 时间戳、实际关节和实际 TCP 位于同一包，优于分别查询产生的两条主机查询区间；同包不能证明所有底层传感器严格同时测量。
- SDK 1.18.4 的结构为 804 bytes，当前包为 784 bytes；额外 20 bytes 属于后续 IO 尾部。诊断只解码实际存在的前缀，不把缺失字段的默认零值当成有效反馈。
- 新通道 TCP 姿态是 `[rx, ry, rz]` 旋转向量（轴角），生产 `tcp_mm_rad` 约定为 `[x, y, z, roll, pitch, yaw]`。需要保留原始表示并显式转换。离线转换后与普通查询 RPY 差值最大约 `2e-5 rad`，位置差最大约 `0.005 mm`；两份数据非同时取得，不能用此差值宣称动态精度。[SDK 反馈定义](https://raw.githubusercontent.com/xArm-Developer/xArm-Python-SDK/master/xarm/x3/report.py)
- 本次 `monitor_device_type=0`，无有效夹爪监测。夹爪继续作为独立来源；约 247 Hz 报告不代表夹爪同频率刷新，未启用字段中的 0 不能当作实际位置。
- 静止下的少量数值变化不足以证明约 247 Hz 的测量更新。需在明确运动窗口验证新通道的状态变化、缓存和时间关系。

### 4.3 尚缺少的准确时间依据

官方定义了微秒单位，但未明确 epoch 及时间戳对应编码器测量、控制周期还是报告组包。实测值明显不是当前 Unix 时间；不据此推断一定从开机计时。

```text
host_received = 时钟比例 × device_timestamp + 时钟偏移 + 传输/排队时间
```

单向接收记录可以分析频率、漂移和排队变化，无法唯一分离固定时钟偏移与固定传输延迟。用最小到达差或直线拟合建立的映射仍有未知固定偏差。要在准确共同时间上对齐相机与机器人，需要验证过的时钟同步依据或可观测共同事件的标定，并记录方法及误差范围。没有在采集时留下这些依据，不能承诺仅靠原始 timestamp 在离线恢复。

## 5. 通信负载与延迟对比

三台相机和 USB 网卡均位于同一个 xHCI 控制器下。`fixed_1` 使用独立 5 Gbps USB 端口；`wrist`、`fixed_2` 和机器人 USB 网卡共用 5 Gbps Hub。网卡以太网协商为 1000 Mbps 全双工。

两路共享 Hub 图像 payload 按 YUYV / RGB8 口径约 **294.9–442.4 Mbps**，不含协议开销。RGB8 可能由 SDK 在主机转换，所以该值不是实测 USB 线速；视频压缩减少最终磁盘占用，不减少相机到主机的捕获带宽。[RealSense 帧管理说明](https://dev.realsenseai.com/docs/frame-management/)

两个阶段各 60 秒，均为只读关节/TCP 各 30 Hz、夹爪 20 Hz 和原约 5 Hz 反馈；第二阶段并发三路 RGB。没有运动、预览、PNG 写盘，也没有并发新 TCP 30000 通道。

| 指标 | 不开相机 | 三路 RGB 并发 |
| --- | ---: | ---: |
| 关节+TCP 成对查询 P99 | 0.976 ms | 0.902 ms |
| 夹爪整组查询 P99 / 最大 | 5.335 / 6.004 ms | 4.909 / 8.761 ms |
| 网卡平均收发合计 | 0.240 Mbps | 0.240 Mbps |
| 关节/TCP、夹爪有效应答 | 约 30、20 Hz | 约 30、20 Hz |
| 查询错误、网卡错误/丢弃计数增长 | 0 | 0 |

同一并发区间三路相机为 **29.987 / 29.987 / 29.964 fps**，设备帧号缺口均为 0。未观察到查询 P99 恶化，但不能把较低数值解释为相机提高性能，也不能外推到新高频状态流加完整录制的负载。夹爪查询区间包含多个顺序寄存器读取，不是原子测量。

## 6. 后续采集端是否只需原始时间戳

**可以将目标定为“采集保留原生数据，离线生成对齐 observation”。但时间戳必须和数据、时钟解释及来源身份一起保存。** 不要求在线插值或给每台电脑填写固定 latency 常数；已经丢失的数据和时钟依据无法通过后处理补回。

以下是建议的最低信息要求，尚不是当前 v2 全部已经提供的能力：

| 需要保留 | 用途与要求 |
| --- | --- |
| 原生图像和状态 | 保留实际捕获帧、每次实际返回的状态；连续状态与离散状态分别解释，不用插值值覆盖原始值 |
| 原始设备时间 | 保留原值、单位、时间域、对应事件；SDK 映射时间与硬件原始时间分开标注。设备不提供时明确缺失，主机时间不冒充设备时间 |
| 主机接收/查询时间 | 发现排队、断连和迟到，辅助时钟分析；保留 monotonic、会话身份、UTC 对照，查询来源保留查询区间 |
| 时钟映射依据 | 记录设备与主机时钟关系、同步/标定观测、方法、有效区间和不确定性；重启、回绕或跳变形成新时间段。精确映射未知时明确标注 |
| 来源与文件索引 | 角色/序列号、设备帧号、独立采集序号；视频文件/帧索引/PTS 与来源帧一一关联，重复引用保持原始时间和身份 |
| 数据解释 | 单位、关节顺序、TCP/坐标系与姿态表示、夹爪原始量及可用性、相机配置、设备/软件版本 |
| 连续性和完整性 | 帧号缺口、缓存复用、查询失败、队列丢弃、时钟重置、录制起止/复位/故障边界，写盘和视频索引校验；不能补时间戳掩盖缺口 |

### 6.1 当前 20 Hz 视频限制了离线重新选帧

当前相机捕获 30 fps，但 raw v2 只保存按接收时间选中的 20 Hz 图像。未选帧没有留下图像，不会因增加时间戳而重新出现。已有数据可以做时间解释和有限重配对，无法恢复完整 30 fps 的选择空间。

如果希望对齐完全留给离线，建议下一版保存三路**原生约 30 fps 压缩视频及逐帧时间索引**、原生高频机器人状态，再构造 20 Hz observation。编码需要验证帧顺序与映射，采样时间与视频定位时间分别保存；不通过补帧/丢帧伪造规则时间轴。仅保存未选帧的时间戳而没有图像仍不够。

这会改变当前 v2 的“每路视频帧数等于 observation 数、视频帧 k 对应 observation k”约定，需要新的原生流层或格式版本及读取/检查支持，不能仅改 fps。另一种较小的方案是在采集端等待缓冲、按来源时间先选定 20 Hz 帧，但会提前固定选择，后处理自由度较低。本次没有实施或决定格式迁移，已有 v1/v2 保持原样。

### 6.2 离线对齐与插值边界

- 图像优先选择真实最近帧。理想稳定 30 fps、无缺帧、时钟准确且目标时间有双侧覆盖时，每路距目标最多约 16.7 ms，两路最坏仍可差约 33.3 ms；实际保存每路偏差，不伪称同时曝光。
- 当前 30 mm/s、0.15 rad/s TCP 限速下，16.7 ms 对应约 0.5 mm、0.143°，仅为量级估算，不是像素误差保证。腕部近景、夹爪接触和遮挡变化需检查实际数据。
- 逐像素线性混合两张图会产生重影风险，不能当成真实中间帧。首版不需要合成图像补帧。
- 连续关节/位置可在有效前后样本间插值；关节处理角度跨界，姿态使用旋转插值。离散状态不线性插值，不跨复位、断连或长缺口插值，也不把外推标为测量。
- 片段首尾不一定有足够的前后样本。未来需在同一连续记录段保留短暂边界缓冲，或裁剪到所有来源共同覆盖的区间；不得借用下一次复位后的样本补齐上一条轨迹。
- 派生数据记录目标时间、原始来源引用和处理方法，原生数据保留。插值不会消除时间戳的不确定性，也不能保证突变过程线性。sim 可记录精确的仿真步时刻，真机记录设备时间与误差，两者共享语义而不伪造相同精度。

## 7. 后续验证顺序与证据

1. 确认新报告时间戳语义及跨设备时钟映射；无法确认的部分保留不确定性。
2. 用户通过原有遥操运动时，以只读旁路验证状态变化节奏；再验证三路相机、高频原生状态保存和控制同时运行的负载。夹爪单独核对。
3. 决定原生图像保存还是采集端提前选帧，形成独立格式/实现计划，再接入采集；保持现有运动反馈与复位行为。
4. 离线生成 20 Hz 网格，报告来源偏差、时钟不确定性和无效片段，用数据评估精度。
